# BahirLedger Flutter client

Flutter client with email/password signup, sign-in, account-only email verification and separate durable onboarding, plus an explicitly unprotected local project/accountability demo. Unverified users land on the verification page; a verified `/me` or confirmation response opens the account page, which separately loads `/onboarding` for organization setup/membership and invitations. Verification alone never grants membership; membership never grants project/policy/financial access. Durable offline storage, project APIs, custom policy and synchronization are not implemented.

## Managed sign-in setup

- Install dependencies with `flutter pub get`. Supply the API **origin** at build/run time using `--dart-define=API_BASE_URL=https://api.example.com` (no path, query, fragment or embedded credentials).
- The default is `http://localhost:8080` for local development. HTTP is permitted **only in debug builds**, and only for exact `localhost`, `127.0.0.1`, or `[::1]` loopback hosts. Profile/release builds require HTTPS, including for loopback. Invalid configuration shows a safe configuration screen instead of sending credentials. Do not use cleartext LAN or production origins.
- A backend implementing the contract below must run separately for actual use. Follow its [private-properties workflow](../b/README.md#private-properties-workflow): edit private database/SMTP values in the editor, never chat, and use normal `./mvnw spring-boot:run` from the backend directory. No launcher, environment-file loading or legacy account provisioning is required; register through the UI. A signup `503` can leave a pending account without a session: sign in and resend verification rather than repeatedly registering. Durable organization setup and owner-shared invitation codes are implemented; password reset is not.
- For web development, pin the frontend origin to the backend template's `http://localhost:8765`, using `--web-hostname=localhost --web-port=8765`. With the debug default API origin `http://localhost:8080`, set both `bahirledger.auth.web-origin` and `bahirledger.mail.verification-web-origin` to that exact frontend origin in the private backend properties; change both if the web port changes. `http://127.0.0.1:8765` is a different origin. The template explicitly permits loopback HTTP email links without selecting the H2 profile. Remote HTTPS deployment needs a reviewed backend CORS policy; the current backend allowlist is loopback-only, not general remote-origin support.
- CORS must allow preflight `OPTIONS`, `Content-Type` and `Authorization` for the exact auth and onboarding methods/routes in [OpenAPI](../b/src/main/resources/contracts/openapi.yaml), including the UUID-shaped invitation revoke route, never a subtree. No wildcard/cookie credentials are required. An HTTPS page needs an HTTPS API to avoid mixed content. CORS/network failures intentionally use generic connectivity errors. All transport route arguments are suffixes; the transport adds `/api/v1` exactly once.
- Native Android internet permission and macOS outgoing-network entitlements are included. Android emulator `localhost` refers to the emulator, not the host: use development port forwarding or a trusted HTTPS endpoint rather than weakening the URL policy for `10.0.2.2`. Platform transport-security rules still apply; no broad Android cleartext or Apple ATS exception has been added. If debug loopback HTTP is blocked by the target platform, use trusted HTTPS (or a narrowly scoped, debug-only platform exception). Platform folders are not release certification.

## Session and HTTP contract

- `POST /api/v1/auth/register` sends JSON `{displayName,email,password}`; `POST /api/v1/auth/login` sends `{email,password}`. Name/email are trimmed, password is not. Both expect `200 {accessToken,expiresAt,user}` with absolute UTC ISO expiry and `user: {id,email,displayName,emailVerified}`. Text fields must be nonempty strings and `emailVerified` must be a boolean: missing/string/numeric values fail closed. New and existing unverified accounts return `false`.
- Signup/sign-in completes only after bearer `GET /api/v1/me` succeeds with the same account ID. The `/me` status is authoritative for the UI, including `false` after a `true` login response. Unverified login permits only account/verification operations. A verified status is not organization authority.
- `401` login errors use the generic “Email or password is incorrect.” message. `400`, `429`, other HTTP errors, malformed responses, network errors and timeouts have fixed safe messages; response bodies and transport exception details are never shown or logged. No automatic retry or refresh is performed.
- `POST /api/v1/auth/logout` uses the bearer token and expects `204`. Local identity and token are cleared **before** waiting for the server. Failures/timeouts warn that remote revocation was not confirmed. Each HTTP exchange has a 15-second timeout and redirects are rejected, including on native platforms.
- `SessionController` is a root-injected `ChangeNotifier`. `BahirLedgerApp` owns and disposes its session, including an injected session; callers should not share it with another root. `AuthTransport` similarly owns its injected HTTP client. Tests can inject `MockClient` and a matching clock into both session and transport. The `demoBuilder` is independently injectable.
- The token is private to `AuthTransport`, **in memory only on every platform**. There are no cookies, localStorage, sessionStorage, preferences, disk/keychain token storage or session restoration. The web adapter implements `package:http`'s client interface using Fetch with `credentials: omit` (the standard BrowserClient otherwise permits same-origin cookies), `cache: no-store`, and redirect rejection. Native uses `package:http` without a cookie jar.
- Expiry is absolute, at the server deadline and never later than 30 minutes from the login attempt. A timer and application-resume check clear local state; activity does not extend it. Restart/web reload signs out locally. Closing the app is **not** confirmed remote revocation; the server session can remain until expiry. Aborted/timed-out login or failed `/me` can likewise leave a server session until its deadline, even though no local authenticated state survives. Managed Dart strings cannot be securely zeroized, but the password controller is cleared immediately after a valid submit and again on disposal.
- “Explore demo (local sample data)” is the only normal application route into `Shell`/`ProjectsPage`. Its disclaimer remains visible on nested sample screens. Demo edits remain local prototype data and convey no membership, permissions or backend project access. Existing direct `Shell` tests remain supported.

## Email verification and links

- Unverified signup/login shows the account email, a masked manual token/link field, explicit **Confirm email**, **Resend verification email**, **Check verification status**, **Sign out**, and the separate unprotected demo. These account operations are serialized; repeated/overlapping clicks cannot send concurrent confirmations/refreshes/resends. Signout remains available during requests.
- Confirmation sends bearer `POST /api/v1/auth/email-verification/confirm` with JSON `{token}` and expects `200 UserView` with the same ID and `emailVerified: true`. Tokens are exactly 43 base64url characters, expire after 30 minutes and are single-use. The account bearer and its original deadline are unchanged. `400` (including `invalid_verification_token`) shows a fixed invalid/expired/reused/wrong-account message, not password advice or a backend-body echo. `401` clears the entire session; `429` asks the user to wait; `503` reports mail/service unavailability. No automatic confirmation or retry is performed.
- Resend uses bearer `POST /api/v1/auth/email-verification/resend` with **no body**, expecting `204`. It reports request acceptance, not guaranteed delivery. Already verified accounts receive `204` without new mail. Success and verification `429` start a local 60-second resend cooldown; backend throttling remains authoritative, including after reload. `503` does not claim success. A fresh `/me` checks verification and can downgrade the UI back to unverified. Malformed or different-account responses clear the session. Logout, expiry, disposal and new sign-in invalidate old responses; none can resurrect a session.
- The backend email link is its configured `bahirledger.mail.verification-web-origin` plus `/#/verify-email?token=TOKEN` (not the Flutter-native `FRONTEND_ORIGIN` define). On web, the trusted origin is **the running app's exact origin**, independent of `API_BASE_URL`. The conditional `package:web` adapter captures initial URL and hash/history navigation, then synchronously replaces the current browser URL with `/#/` before parsing/notifying widgets. It does not push a secret-bearing history entry or copy history state. Flutter always starts at a safe root route; incoming tokens never become route settings or default-route error text. Missing/malformed links show fixed guidance and are also scrubbed.
- Only the exact trusted verification fragment (or `/verify-email?token=TOKEN` path) is accepted; credentials, other origins/ports/schemes, other paths, duplicate/extra parameters and malformed tokens are rejected. No remote link is followed or looked up. Use the backend's **fragment link**: a manually entered path/query URL may already have reached hosting/proxy logs before app code runs. URL scrubbing cannot remove browser/email-provider records created before app startup, so avoid third-party URL analytics and do not log incoming links.
- Signed-out links are held **only in memory** across sign-in/signup navigation. Sign in to the matching account, then explicitly confirm; simply opening a link never sends confirmation. Cancel clears pending input. Confirmation submission (including invalid input), cancel, resend/status actions, signout and page disposal clear the input controller. Session expiry and app disposal discard pending data; no preferences, browser storage or clipboard persistence is used by the app. Managed strings cannot be securely zeroized.
- Native apps support manually pasted raw tokens. To accept full trusted links on native, compile with `--dart-define=FRONTEND_ORIGIN=https://app.example.com` matching the backend email-link origin (same strict HTTPS/debug-loopback origin policy). Without this define, paste only the raw token. Actual OS universal/app-link registration is **not** part of this slice. `VerificationLinkSource` and `VerificationLinks` are injectable for deterministic initial/navigation/scrubbing tests; the app owns and disposes the supplied links and session.
- There is **no real email delivery guarantee**. SMTP/outbox enablement is a backend/operator concern; the frontend neither sends mail itself nor assumes delivery after signup or resend.

## Durable onboarding — implemented 2026-10-03

- [Typed onboarding models](lib/src/auth/onboarding.dart), [transport](lib/src/auth/auth_transport.dart), [session controller](lib/src/auth/session_controller.dart) and [account page](lib/src/pages/account_page.dart) use the existing active verified bearer; `/me` stays identity-only and the bearer deadline never extends. Account entry and explicit status refresh load separate `/api/v1/onboarding` context to resume durable setup; application resume checks local session/code expiry, not an automatic context fetch. Unknown/malformed states fail closed; a loaded organization is membership only, not an authorized project workspace.
- With no membership, save/edit a proposed organization name, resume its durable setup after re-login, cancel or explicitly activate it. Pending state is an **account-scoped restricted workflow, not a separate bearer or grant**. Fixed **24-hour** expiry is server-authoritative; edit does not extend it. No organization or owner authority exists until atomic activation. One org/account includes revoked/suspended memberships, so no tenant switcher or re-enrollment bypass.
- `OWNER` can issue/list/revoke invitations; `MEMBER` sees membership only. **No invitation email or link is sent or supported**: the owner securely shares a private code out of band. Its raw value is returned once, kept ephemerally, and shown only after refreshed owner context and matching pending invitation are confirmed. Copy is explicit; the user's clipboard after copy is outside app cleanup guarantees. Never log/store/share codes in URLs or analytics.
- Recipients paste the raw code, explicitly preview the organization/expiry, then explicitly accept. The backend requires the **exact normalized verified recipient email plus the secret**, strict **seven-day** validity and single-use consumption; it persists only a SHA-256 digest. Preview reserves nothing; wrong/revoked/expired/replayed codes use safe generic failures. Acceptance atomically cancels pending setup and creates `MEMBER` with audits; a lost success is recovered by status refresh, not automatic replay.
- Verification/onboarding share a serialization gate and operation epoch. Signout, expiry, account changes, dismissal and disposal invalidate stale operations; transport cancellation also invalidates its generation so a dismissed late `401` cannot clear a newer live session. Inputs, previews and issued secrets are ephemeral and cleared on relevant lifecycle/cancel/account actions. No automatic mutation retries, persistent tokens or silent authority restoration.
- Server limits: mutation/preview **20/account, 80/direct source, 200/global per five minutes**, **10,000 per-process keys**; durable **100 open invites/org, 10 issued/owner per rolling 24 hours**, list latest **100**. Issuing again consumes budget; revocation does not restore issuance budget and a lost raw code cannot be recovered. Tenant `429 rate_limited` uses safe wait guidance. Every mutation/audit commits atomically; exact routes, bounded bodies and no-store responses remain enforced.
- These `OWNER`/`MEMBER` choices are slice-specific, not universal role policy. No project/policy/finance grants, destructive member/owner administration or custom policy UI exists. [Onboarding tests](test/auth/onboarding_test.dart), [widget tests](test/auth/onboarding_widget_test.dart) and [race tests](test/auth/onboarding_race_test.dart) cover the new mocked contract, workflows and late-response behavior; they are not live backend/browser certification.

## Backend and access direction

The [backend build definition](../b/pom.xml) establishes Java 21 / Spring Boot; approved direction is PostgreSQL modular monolith, REST/JSON/OpenAPI, explicit push/pull sync, S3-compatible evidence and Python-owned AI processing/derived analytics. Java owns business authority; AI remains planned, with no provider selected. See the [root overview](../README.md) for current scope, [architecture](../architecture.md), [API design](../api-design.md), and [AI ownership](../ai-analytics.md). This frontend integrates the managed account-authentication and separate durable-onboarding contracts described above.

An org is an independent workspace/tenant, not a legal entity. Invite-only membership and restricted bootstrap are implemented through explicit verified-bearer operations, never inferred from successful login. Optional SSO/external-browser OIDC/PKCE and general tenant/project authorization remain future work.

Authority is configurable by org/project, including self-approval, scoped grants and delegated role/approval administration bounded by mandatory rules. Role templates are optional. [Old review decisions](docs/dec/decisions.md) and [workflow sketches](docs/workflow/1_projectWorkFlow.md) are historical prototype examples, not universal policy.

Offline timings and online-by-default approvals remain proposals. No authoritative offline approvals or instant disconnected revocation; pending work must be retained encrypted for later reconciliation. The current prototype does not implement those protections.

Shared decisions and specifications are version-controlled at the root: [decisions](../decisions.md) and [auth/access](../auth-access.md). Local implementation context, review records and development plans belong only under the repository-root ignored `docs/` directory, not this source tree. Historical UI screen numbers are examples, not current development roadmap numbers; numbering history is preserved in local plans.
