# Approved architecture and implementation boundary

Updated: 2026-10-03. Approved direction, not a claim that all capabilities are implemented. See [README.md](README.md) and [b/README.md](b/README.md) for current source scope. Development plans and verification history remain local and separate.

## Shape and ownership

- **Flutter client** in `ui/`: presentation, local drafts/cache and eventual encrypted pending commands. Client checks improve UX, never replace server authorization.
- **Java Spring Boot modular monolith** in `b/`: REST/JSON, explicit application commands, server authorization and transactional domain changes. Keep module boundaries inside one deployable service; do not introduce microservices now.
- **PostgreSQL**: deployment target for authoritative tenant-scoped records, policy versions, memberships and attributable history. JDBC/Flyway accounts, verification and additive V3 durable organization/bootstrap/membership/invitation/audit storage now exist; the local profile uses file-backed H2 outside the checkout. Parent disposable PostgreSQL 16 onboarding state tests passed with clean V1–V3 migrations in isolated per-test schemas, not existing-database upgrade or deployment certification. Onboarding mutation/audit already share a transaction; future domain mutations and outbox records must do likewise.
- **OpenAPI**: versioned API contract committed with the backend; runtime endpoints must match it. The [current static contract](b/src/main/resources/contracts/openapi.yaml) is not a public documentation endpoint. See [API design](api-design.md) for protocol choices.
- **Explicit push/pull synchronization**: client submits idempotent proposed commands and pulls scoped changes using a version/cursor contract. Server revalidates current membership, permissions, policy and conflicts; local acceptance is not server acceptance. Full synchronization is planned, not present today.
- **S3-compatible evidence storage**: private objects plus tenant-scoped metadata and controlled upload/download authorization; no public bucket or object-key-as-permission design. Evidence integration remains future work.
- **BahirLedger-managed identity by default; optional organization SSO**: Flutter/Java implements account-only signup, direct email/password authentication, BCrypt (cost 12), and opaque 30-minute bearer tokens, with no authentication server, OIDC flow or cookie authentication. Client tokens and backend digest sessions are memory-only; accounts and verification state are durable. Required `emailVerified` defaults false for new, migrated and locally provisioned accounts. Same-account authenticated confirmation consumes a single-use 30-minute SHA-256-digest token; resend rotates it with a durable 60-second cooldown and bounded per-process rate limits. Separate verified-bearer bootstrap/invitations are implemented without an IdP prerequisite. Optional SSO requires reviewed providers and verified linking, never email auto-linking. See [auth/access](auth-access.md).
- **Python AI and analytics component**: owns model-provider integrations, document processing, embeddings/retrieval and derived analytical data. Consumes explicitly scoped, authorized data/events and produces advisory findings. Java retains business authority; Python cannot independently write authoritative project/financial records. Deploy with the first concrete AI feature; not a prerequisite for the core backend. OpenAI is not selected. See [AI and analytics](ai-analytics.md).

An organization is an independent workspace/tenant, **not a legal entity**. Projects belong to exactly one tenant. Any later legal-entity modeling must be separate. Application accounts join one organization only, by invitation; self-service organization creation is a controlled bootstrap exception, not open membership enrollment. No cross-organization sharing or tenant switching is authorized by this model.

Flutter gates unverified accounts on verification; verified accounts separately load durable `/onboarding` context while `/me` remains identity-only. Verification fragment links are ephemeral and scrubbed from the current browser URL/history entry before UI handling; confirmation is explicit. Native supports manual paste, not OS universal/app links. Invitation codes have no email/link flow. The separate local project demo confers no authorization. Onboarding membership is not full tenant/project isolation, policy administration, production certification or offline access; business endpoints must require verified email, active membership and effective scoped permissions. The internal policy evaluator remains a separate tested primitive.

## Implemented durable onboarding — 2026-10-03

The [service](b/src/main/java/com/bahirledger/backend/onboarding/OnboardingService.java) and [V3 migration](b/src/main/resources/db/migration/V3__onboarding.sql) enforce one organization membership per account, including revoked/suspended records. Pending setup is a durable account-scoped restricted workflow with fixed 24-hour expiry, editable/cancellable/resumable on the existing verified bearer; it issues no separate grants and creates no organization until atomic activation with initial `OWNER` membership and audit. Locks follow account → organization → invitation; all mutations and attributable audits roll back together.

Seven-day digest-only invitation secrets are returned once for secure owner sharing: **no invitation email or link**. Exact normalized verified recipient plus secret is required for preview/accept. Acceptance consumes the invite, cancels pending setup and creates `MEMBER` atomically. `OWNER` only administers invitations; neither role grants project/policy/finance authority. Destructive member/owner administration and custom policy remain future; these roles are implemented-slice choices, not a universal hierarchy. [API bounds](api-design.md#implemented-durable-onboarding--2026-10-03) include per-process mutation/preview throttles, durable issuance caps and bounded lists; they do not supply distributed abuse protection.

Parent final full-JDK-21 Maven `test`: **137 passed, zero failures/errors/skips**, after the backend single-line organization-name fix rejecting embedded ASCII controls. The same **15 `OnboardingStateTest` tests passed independently on disposable real PostgreSQL 16**: isolated per-test schemas, clean V1–V3 migration, concurrency, audit rollback, expiry and digest/recipient binding. H2 additive upgrade and shutdown/reopen also passed. **326 Flutter tests, clean analyzer and release web build** remain implementation-agent results, not parent reruns. See [test isolation and evidence](b/README.md#onboarding-validation--2026-10-03).

The disposable PostgreSQL instance is stopped; user database/private configuration/services were untouched. No PostgreSQL existing-database upgrade, PostgreSQL-backed HTTP/browser/SMTP validation or server restart is claimed. The shared browser tab is the stale old implementation; no new live UI validation occurred. This docs-only pass reran no runtime checks. Live onboarding/browser/native and production validation remain gates, independent of earlier verification evidence.

Verification mail is synchronous under an account-row lock: the private configuration template selects Gmail SMTP/587 with STARTTLS; disabled mode remains the unconfigured adapter fallback. A private external file outbox is allowed only with the exclusively local profile. The file outbox is not the planned transactional job outbox and sends no inbox mail. Adapter acceptance is not guaranteed delivery; no durable worker, automatic retry or atomic database/SMTP commit exists. Earlier live HTTP/file-delivery and browser-link/CORS checks passed; full interactive browser/manual verification, SMTP/inbox, PostgreSQL-backed HTTP/mail and native validation remain outstanding (see [historical validation limits](b/README.md#verification-validation--2026-10-03)). Deployment CORS, secret management, distributed sessions/throttles and broader security gates remain open.

Backend runtime settings are direct properties in private, ignored/untracked [b/src/main/resources/application.properties](b/src/main/resources/application.properties), with a credential-free [b/src/main/resources/application.properties.example](b/src/main/resources/application.properties.example). No launcher or environment-file setup is required; the optional H2 profile inherits private CORS/mail values. Follow the [property workflow and secret/artifact warnings](b/README.md#private-properties-workflow): untracking does not erase committed secrets, and packaged resources can contain private credentials.

## Module seams (direction, not implemented modules)

Identity/membership, authorization/policy, projects/workflow, preparation/finance, audit, sync and evidence should expose narrow application interfaces. Tenant context comes from validated identity and membership, never an untrusted organization ID alone. Scope every query, command, event, cache and storage key to the tenant; validate project ownership before evaluating project grants. PostgreSQL transactions provide the authoritative commit boundary. Local durable storage is a separate client choice, gated on supported platforms, encryption and recovery requirements.

Use structured org/project policies rather than a fixed project-management methodology. Workflow examples, RACI labels and role templates are optional; mandatory security constraints cannot be overridden by organization or project configuration.

## Why this division

Java/Spring Boot supplies a mature strongly typed ecosystem for transactions, validation, authorization, testing and domain workflows. Java decimal arithmetic and PostgreSQL constraints support financial correctness, but neither replaces explicit invariants and concurrency tests. Kotlin is a viable ecosystem alternative, not an additional implementation language selected here; Go/TypeScript are not needed as extra gateways or services.

Python provides the ecosystem for AI-provider orchestration, data science, document extraction and specialized ML. Java can call model APIs directly; the division is an ownership choice, not a Java limitation. Keep the core as one deployable Java application; add one Python worker rather than decomposing all business modules into services.

## Data and deployment boundaries

- Java owns business records, authorization, financial invariants, audit and synchronization. Python owns derived data (extracted text, embeddings, features and advisory outputs) behind scoped interfaces.
- A shared PostgreSQL installation with separate schemas/credentials is a possible cost-conscious start; do not give Python unrestricted table access. Dedicated databases or tenant deployments may be required by future isolation needs.
- Use current-state tables plus attributable append-only events and a transactional outbox where needed. Full event sourcing is not required; an append-only application API is not tamper-proof storage.
- Start durable AI jobs with PostgreSQL-backed delivery if sufficient; brokers such as Kafka/RabbitMQ are deferred until justified. Define retries, deduplication and recovery before delivery.
- The Java core remains available if Python or the model provider is unavailable. AI failures must not roll back independent business transactions or bypass normal workflows.
- Keep a typed injected client store/repository, immutable updates and stable IDs; keep demo fixtures separate from durable records. Framework-native Flutter state is sufficient until a concrete need warrants a library.
