# Decisions and gates

Updated: 2026-10-03. Keep unresolved policy explicit. Implementing a proposed default does not make it an approved product decision. This is the shared decision register; execution steps and results belong to local development records.

## Confirmed inputs

- Flutter app under `ui/`, Java backend under `b/`; architecture, access, product and API/AI specifications at the repository root are version-control eligible. Only development notes, context, plans and history remain in root `docs/`, Git-ignored.
- Work in small testable, reviewable increments. Architecture approval does not certify implemented security or authorize all features at once.
- Approved [architecture](architecture.md): Java Spring Boot/PostgreSQL modular monolith, REST/JSON + OpenAPI, explicit push/pull sync, S3-compatible evidence; BahirLedger-managed identity by default and optional organization SSO. OIDC is proposed for future SSO interoperability, not the current sign-in protocol.
- Approved [AI ownership](ai-analytics.md): Python handles AI-provider integration, processing and derived analytics; Java retains business authority and authoritative data. Python cannot independently mutate approvals, project states, permissions or financial records. Deploy with the first concrete AI feature; core Java workflows must remain available without it. OpenAI, specific SDKs/models, FastAPI and a broker are not selected dependencies.
- [API decisions](api-design.md): REST/JSON + OpenAPI for clients, explicit REST synchronization and authorized object transfers; versioned durable jobs/results for Python. Optional internal HTTP for interactive AI and optional SSE later. GraphQL, gRPC and WebSockets deferred until a demonstrated requirement; mobile background alerts use platform push rather than permanent sockets.
- Self-service org creation; org is an independent workspace/tenant, not a legal entity. One org per application account, invite-only membership, personal devices only. Account-only managed registration/email verification and separate durable bootstrap/invitations/membership are implemented without requiring an organization IdP.
- Structured org/project policy configures self-approval, role/approval delegation by authorized admins, and org-wide versus selected-project authority. Optional role templates, no fixed methodology. Org-delegated overrides are bounded by mandatory rules.
- Restricted managed bootstrap: verify account/email and satisfy controlled organization activation before tenant access; atomically enforce one org/account. Invites bind recipient/org, expire and are one-use; verified email alone is not membership. Optional SSO enrollment will require provider-control verification/test sign-in, trusted registries and issuer+subject binding. Linking requires verified control of both identities, never matching-email auto-linking. External-browser auth code + PKCE/no client secret applies to future SSO only.
- Implemented account slice: Java signup/sign-in, BCrypt cost 12, opaque 30-minute bearer tokens held only in Flutter memory, backend in-memory SHA-256 digest sessions and JDBC/Flyway accounts. No auth server, OIDC, cookie authentication or refresh tokens. Required `emailVerified` defaults false for new/migrated/local accounts. Same-account bearer confirmation uses single-use 30-minute verification tokens persisted only as SHA-256 digests; resend rotates them with durable 60-second cooldown and rate limits. Flutter verification/account gates confer no membership. PostgreSQL is the deployment target, local H2 files are external, and disposable PostgreSQL 16 onboarding state tests passed as detailed below; no production-ready claim.
- Verification delivery uses direct private properties, with Gmail SMTP/587 and STARTTLS selected in the credential-free template; disabled mode remains the unconfigured adapter fallback. No launcher or environment setup is required; see [private configuration and secret/artifact warnings](b/README.md#private-properties-workflow). SMTP or an exclusively local private file outbox is not guaranteed inbox delivery or a durable mail worker. Signup failure may leave a pending account; recover through login/resend. Fragment tokens are ephemeral with current URL/history-entry scrubbing and explicit confirmation; native manual paste is supported, OS universal/app links are not. Earlier live HTTP/file-delivery and browser-link/CORS checks passed, not full interactive browser/manual, SMTP/inbox, PostgreSQL-backed HTTP/mail or native validation; see [historical validation limits](b/README.md#verification-validation--2026-10-03).
- [Legacy decisions](ui/docs/dec/decisions.md) about required review and reasons are historical prototype rules, not universal policy. Preserve regression behavior until a reviewed configurable replacement.
- [Offline recommendations](auth-access.md) (seven days, five minutes, 30-day exceptions, online-by-default approvals) remain unaccepted proposals. Revocation reaches disconnected devices later; pending work retained encrypted; no authoritative offline approvals.

## Superseded identity decision — 2026-10-03

The earlier mandatory organization SSO, no-local-password-service and provider-required bootstrap direction is **superseded**, not an additional active rule. The accepted replacement is managed identity by default with optional organization SSO. Provider-control/test-sign-in gates remain relevant when enabling SSO, not prerequisites for managed signup or organization creation. This changes identity onboarding only: invitation-only membership, one org/account, personal devices and configurable authorization remain unchanged.

## Implemented onboarding slice decisions — 2026-10-03

These choices describe the delivered bounded slice, **not a universal role hierarchy or completed production authorization policy**. Source of truth: [service](b/src/main/java/com/bahirledger/backend/onboarding/OnboardingService.java), [OpenAPI](b/src/main/resources/contracts/openapi.yaml) and [access boundary](auth-access.md#implemented-durable-onboarding--2026-10-03).

- Separate `/onboarding` on the existing active verified bearer; `/me` and auth shapes/deadlines unchanged. Pending means an account-scoped restricted workflow, not a special bearer/session/grant. Save/edit/cancel/resume has a fixed 24-hour expiry; edit never renews it. No organization/owner authority until atomic activation with membership and audit. Reuse of a committed activation ID is retry-safe.
- One org/account includes retained suspended/revoked membership. There is no switch/re-enrollment bypass. Bootstrap activation yields `OWNER`; acceptance yields `MEMBER`. Only `OWNER` administers invitations; neither grants project/policy/finance permissions. No destructive membership/owner admin, owner transfer or custom policy implementation; recovery/last-owner gates stay open.
- Seven-day single-use **owner-shared private codes, no invitation email or link**. Exact normalized verified recipient plus secret is required; only SHA-256 digest persisted, raw code returned once. Preview/accept/revoke are implemented. Acceptance and pending cancellation/member creation/audits commit atomically; issue retry is not idempotent and cannot recover a lost code.
- Every mutation commits attributable audit atomically; account → organization → invitation lock order. Lazy expiry views are not mutation/retention workers. Application audit is not tamper-proof storage or comprehensive security monitoring.
- Mutation/preview budgets: 20/account, 80/direct source, 200/global per five minutes; 10,000-key per-process bound. Durable caps: 100 open/org, 10 issued/owner per rolling 24 hours; list latest 100. Exact routes, 4096-byte bodies, no-store and no ambient-cookie auth remain enforced; production distributed limits are still future.
- Flutter integrates the durable workflow with ephemeral invitation codes and lifecycle/stale-response guards, not authorized demo projects. Parent final full-JDK-21 Maven `test`: **137 passed, zero failures/errors/skips**, after the backend single-line organization-name fix rejecting embedded ASCII controls. The same **15 `OnboardingStateTest` tests passed independently on disposable real PostgreSQL 16** with isolated per-test schemas: clean V1–V3 migration, concurrency, audit rollback, expiry and digest/recipient binding. H2 additive upgrade/reopen also passed. **326 Flutter tests, clean analyzer and release web build** remain agent results, not parent reruns; see [evidence and isolation](b/README.md#onboarding-validation--2026-10-03).
- The disposable PostgreSQL instance is stopped; user database/private configuration/services were untouched. No PostgreSQL existing-database upgrade, PostgreSQL-backed HTTP/browser/SMTP validation or server restart is claimed. The shared browser tab is the stale old implementation, not new UI validation. Full interactive browser onboarding/verification, SMTP/inbox, native and production gates remain open. Earlier account verification checks remain dated evidence, not onboarding validation.

## Implementation guidance (not implementation claims)

- One injected project repository/store, stable IDs, typed models/results, immutable updates; keep widgets thin and existing UI working.
- Small framework-native state mechanism is sufficient initially; no state-library migration without a concrete need.
- Durable project mutation plus event append should be atomic. An append-only local API is not a tamper-proof ledger.
- Separate demo fixtures from real persisted records; initialize sample data only explicitly.
- Keep backend/auth, sync, cryptography and finance-ledger changes separate from local state repairs. Do not confuse approved architecture with completed security. Deployment starts small; neither a dedicated broker, full event sourcing, nor multiple Java business services is required.
